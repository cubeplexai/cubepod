# CubePod 0.8.0

## 功能与改进

- **统一 `/workspace` 块卷生命周期管理（[CEP-0030](/zh/ceps/0030-unified-workspace-block-volumes/)，`#150`）。** 在 `/volumes` API 中新增 `type: "shared" | "block"`（默认 `"shared"`），并将 `"block"` 卷映射到 `PodBoxSpec.VolumeMounts[].Type: "block"`，直接以 ReadWriteOnce 裸块设备（`VolumeDevices`）挂载至 `/workspace`。引入基于 Kubernetes PVC 注解（`cubepod.io/attached-sandbox`、`cubepod.io/attach-lease-expires`）的 CAS 租约与控制器隔离护栏（`WorkspaceVolumeLeaseLost`）、工作区与 RootFS 独立 CSI CoW 克隆、`PodWarmPool` 块卷保护，以及 `cubepod volume migrate-legacy` 迁移工具（配合活跃 `PodBox` 自动接管与 `volumes.allowLazyLegacyClaim`）；上述能力受 `featureGates.blockWorkspaceVolumes`（`CUBEPOD_FEATURE_BLOCK_WORKSPACE_VOLUMES`）门控。
- **Firecracker 共享持久卷 NFSv3 传输（[CEP-0031](/zh/ceps/0031-firecracker-volume-nfs/)，`#157`、`#158`）。** 新增 `cubepod-volume-nfs` 用户态 NFSv3 租约代理服务（`cmd/cubepod-volume-nfs`、`pkg/volumenfs`、Helm `volume-nfs.yaml` 及新镜像 `ghcr.io/cubeplexai/cubepod-volume-nfs:v0.8.0`）、控制器租约预注册（`pkg/controller`）以及 `podd-init` 内置无辅助程序依赖的 `libc::mount(2)` NFSv3 挂载（无需 `nfs-common` / `mount.nfs`）。`pkg/egress` 新增内核 `rpciod`（`skuid 0`）ClusterIP NFS 端口放行，默认开启 `featureGates.firecrackerVolumeNFS`，并提供实验性固定 Firecracker NFSv3 Guest 内核构件（`deploy/k8s/kata/guest-kernel/fc-nfs1.pin.json`、`test/guest-kernel/README.md` 与 `CEP0031_FC_NFS_GATE` 门禁）。
- **彻底统一持久卷命名体系（`#145`）。** 在 CRD（`PodBox.spec.volumeMounts`）、Go（`K8sVolumeMounts`、`CUBEPOD_VOLUMES_*`、`cubepod_volume*`）、Rust（`podd_init_volume_bind_duration_ms`）、Helm（`volumes.*`、`featureGates.k8sVolumeMounts`、`volumes-pvc.yaml`）、Prometheus 告警规则（`deploy/monitoring/volumes-alerts.yaml`）、Docker Compose 与中英文文档中彻底完成 `e2bVolumes` -> `volumes` 命名切换。

## 问题修复

- **PodTemplate `/status` 持久化与 BuildKit 兼容性修复（`#146`、`#148`）。** 修复模板标签构建期间 `PodTemplate` `/status` 子资源持久化与冲突刷新逻辑，为 Helm BuildKit 缓存 PVC 增加 `storageClassName` 配置，并兼容 Kubernetes `<1.30` 的 AppArmor 注解格式。
- **Volume HA、Docker 块卷克隆与存储目录权限修复。** 保留高可用网关场景下 `volumeMounts` 兜底回退、修复 Docker 块卷工作区 CoW 克隆与租约清理逻辑，并将 volume store 目录权限调整为 `0710`，确保 `cubepod-volume-nfs` 正常遍历租户与卷目录。

## 已知问题

- **Kata + Firecracker 块设备热插拔竞态问题（`#120`）。** 在 Kata Containers 搭配 Firecracker（`kata-fc`）运行时，沙箱 Pod 仍偶发在容器启动前因 `virtio-mmio` 块设备热插拔竞态触发 `EIO: I/O error`（`EXT4-fs (vdb): unable to read superblock`）。默认 CI 中 `kata-fc` 的官方 SDK Volume 持久化用例继续因 `#120` 跳过（需显式开启 `CEP0031_FC_NFS_GATE=1` 验证）；**生产 Kubernetes Kata 部署仍推荐默认使用 Cloud Hypervisor（`kata-clh`）**。详见 [issue #120](https://github.com/cubeplexai/cubepod/issues/120)。
- **Firecracker NFSv3 Guest 内核前提要求。** 在 `kata-fc` 上使用 `cubepod-volume-nfs` 挂载持久化共享 `/volumes` 时，需要 Guest 内核内置 NFSv3 客户端支持（Kata 4.4.0 原生内核包默认未开启 NFSv3；仓库已提供实验性固定内核配置 `deploy/k8s/kata/guest-kernel/fc-nfs1.pin.json`）。

## 升级前注意事项

在执行 `helm upgrade` **之前**，请务必先应用更新后的 CRD 清单（包含 `PodBox.spec.volumeMounts[].type` 与统一后的 `volumeMounts` 字段结构）：

```bash
kubectl apply -f deploy/helm/cubepod/crds/
```

升级现有集群前，请确认以下 `0.8.0` 变更与迁移要求：

- **Helm 与环境变量彻底重命名（`e2bVolumes` -> `volumes`）**：将 `values.yaml` 中的 `e2bVolumes.*` 更新为 `volumes.*`、`featureGates.k8sE2BVolumeMounts` 更新为 `featureGates.k8sVolumeMounts`，将自定义 `CUBEPOD_E2B_VOLUMES_*` 环境变量更新为 `CUBEPOD_VOLUMES_*`，并切换至 `deploy/monitoring/volumes-alerts.yaml`。此次重命名不保留旧别名，旧版 `e2bVolumes` 卷存储中的 KMS 信封密钥与加盐租户派生密钥无法直接跨重命名复用。
- **迁移 `0.8.0` 之前的 `/workspace` 历史数据（[CEP-0030](/zh/ceps/0030-unified-workspace-block-volumes/)）**：升级时仍在运行的 `PodBox` 会自动接管原有工作区 PVC；离线或历史工作区 PVC 及本地目录可使用 `cubepod volume migrate-legacy --volumes-dir <dir> --dry-run` 预检并零拷贝迁入 `/volumes`（或在重构沙箱时通过 `volumes.allowLazyLegacyClaim: true` 按需认领）。
- **新增 `cubepod-volume-nfs` 组件与全组件同步升级**：`volumes.nfs.enabled` 会配合默认开启的 `featureGates.firecrackerVolumeNFS: true` 部署 `cubepod-volume-nfs`。请同步升级全部 7 个 GHCR 镜像（`cubepod-controller`、`cubepod-gateway`、`cubepod-egress`、`cubepod-podd`、`cubepod-volume-nfs`、`cubepod-sandbox-base`、`cubepod-desktop`）、`0.8.0` Helm Chart 以及客户端 SDK（`pip install -U cubepod==0.8.0` / `npm install cubepod@0.8.0`）。
